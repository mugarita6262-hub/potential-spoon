# 経緯と教訓（rakuten_room）

変更を設計する前に、必ずこのファイルを読む。新しい不具合を見つけたら、ここに追記する。
全体の構成は ARCHITECTURE.md。

## 進め方の決まり（2026-10-26 ユーザー指示・厳守）

1. **変更する前に、このファイルを読む。** 同じ種類の失敗を繰り返さない。
2. **本番に入れる前に、批判専用のエージェントに点検させる。** エージェントは読み取りだけで、否定の目線から見る。指摘を直したら、その修正も再点検させる。点検を通ってから反映する。
   - **点検エージェントにも、必ずこのファイル（LESSONS.md）を最初に読ませる。** 過去の不具合と運用ルールを共有したうえで、「同じ種類の失敗の繰り返し」と「運用ルール違反」も点検の観点に入れる（2026-10-26 ユーザー指示）。
3. **反映したあと、実際のサーバーの記録で効いたことを確かめてから「直った」と言う。** 手元のテストだけで報告しない。
4. **報告では「確認済み」と「見込み・推測」を分ける。** 確かめていないことを断定しない。
5. 戻せない処理（削除）は、件数ではなく中身を記録で確かめる。

## 決まっている運用ルール

- **削除の対象：** 2025-01-01 より前の投稿だけ（販売終了 → 古い順）。このツールの投稿は、販売終了でも絶対に消さない。
- **再起動の時刻：** コードを反映する再起動は 3:00 に予約する。0:10 は夜のジョブと重なる。
- **反映の確認：** サーバーへ上げる前に、サーバーのファイルが git の HEAD と同じかを確かめる。
- **作業の記録：** サーバーは git ではなく、ファイルのコピーで配っている。

- **10/28〜の実験：** 季節もの1割・「お試し/訳あり」系を足した効果を、日別のクリック数と注文数で、10/18〜27（マラソン 10/24〜27 を含む）と比べる。
